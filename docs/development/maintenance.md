# Сопровождение

Ответственный за выпуск и инциденты — владелец репозитория halsab/isketatar. Канал сообщений — [Issues](https://github.com/halsab/isketatar/issues). В публичном сообщении нужны версия приложения/курса из справки, браузер/ОС, ID материала, шаги и наблюдаемый результат. Не запрашивать полный backup, личную историю, cookies или профиль браузера в открытом issue. Для воспроизведения сначала использовать новую обезличенную тестовую БД.

## Изменение материалов и зависимостей

До правки записать ожидаемое поведение и пример регрессии. Для логики сначала воспроизвести дефект тестом, затем исправить и провести независимое ревью с чистым контекстом. Для простой документационной правки достаточно проверки фактов и ссылок. Коммит завершает исправленный и проверенный шаг.

Редактировать исходники content/, а не src/generated/ или public/runtime/. После изменения корпуса обновить content_version в генераторе tools/build_indexes.py, затем выполнить `python3 tools/build_indexes.py`, `npm run generate` и `npm run check:content`; генератор пересоздаёт content/manifest.json и индексы по исходникам. Правка только версии готового manifest будет перезаписана генератором. Для намеренного изменения исходного формата сначала обновить контракт и tools/schemas/, затем `npm run schema:snapshot` и проверить diff: snapshot не заменяет проверку совместимости. SourceSpan сохраняет привязку к LF-снимку источника.

| Изменение | Требуемая семантика и проверка |
|---|---|
| Только explanation/hint, без нового проверяемого смысла | grading_revision остаётся прежней; регрессия подтверждает прежние mastery/SRS, редактор проверяет объяснение |
| Ключ, формулировка, опция, читаемый контекст | Пересчитать grading_revision штатным генератором; сохранить прежние Attempts, проверить needs_refresh, активную ReviewCard с step=-1/due=now и сохранность suspended-состояния |
| Добавление/удаление обязательного вопроса | Старый сеанс не выполняет новый вопрос автоматически; удалённый ID остаётся в истории/legacy, исключается из текущих знаменателей |
| Новый release при paused session | Сохранять закреплённый пакет и прежний ключ; недоступный/несовместимый draft не проверяется новым ключом |
| Смена progress/content schema или policy | Отдельный план преобразования и чтения старой БД, границы поддерживаемых версий, atomic failure/recovery и forward fix; обычный rollback запрещён при несовпадении контрактов |

Версии политик определены в src/domain/content/types.ts. Канонизация grading_revision — в src/domain/content/revision.ts и генераторе; не присваивать прежний hash изменённому вопросу. Исторический first_mastered_at и самостоятельная оценка новой редакции различаются. Удаление localStorage/IndexedDB не является миграцией. Каждая новая физическая схема требует настоящего versionchange/blocked test и экспорта до изменения; v1 поддерживает только progress_schema1/db_version1.

Зависимости обновлять небольшими связанными группами: проверить upstream changelog/security notices и совместимость с закреплёнными Node/npm, обновить точную версию и lockfile. Не применять `npm audit fix --force` как автоматический способ разрешения advisory. Для шрифтов сохранить лицензии, пересобрать WOFF2 и повторить покрытие/соединение/marks всего корпуса. Версии Actions закреплять полным SHA проверенного официального тега; отдельно читать изменения permissions, runtime и формата artifacts. Не добавлять плановые тяжёлые CI-прогоны без отдельной необходимости.

## Проверки по области изменения

`npm run check` — общая проверка content/docs, границ, типов, unit и инструментов. `npm run build` проверяет итоговый dist и размерные бюджеты. Автоматический допуск PR/main — `npm run test:smoke` (15 ключевых Chromium-сценариев). Полный набор трёх браузеров и performance доступны ручным аудитом Actions; их запускать при соответствующих изменениях из таблицы или перед крупным выпуском. Адресные повторы нужны после исправлений или при новой неопределённости. Не запускать сборку параллельно E2E, не запускать CPU-нагрузку параллельно performance.

| Область | Дополнение к общей проверке |
|---|---|
| Учебное ядро/контент | course, assessment, reading-practice, review; при изменении корпуса полный `@full` проход и retained-сценарии старого содержимого |
| IDB, импорт, черновики | progress, runtime, settings, retained; настоящая IndexedDB трёх движков |
| Worker/bootstrap/update | startup, bootstrap, offline, update, remove-offline, retained и `npm run test:delivery` с реальным PREVIOUS_DIST |
| UI, клавиатура, шрифты | controls, typography, accessibility; геометрия/визуальное ревью, адресная ручная проверка устройства/AT |
| Сборщик, React, CSS, размер ресурсов | build/budgets, startup/release и `npm run test:performance` (5 холодных запусков ×4 страницы) |
| CI/упаковка | `npm run test:tools`, actionlint всех workflow, roundtrip архивов, delivery и локальный published smoke |

Например, `npm run test:e2e -- tests/e2e/progress.spec.ts tests/e2e/settings.spec.ts` выполняет выбранные файлы во всех трёх движках. `npm run test:e2e` — весь набор, включая корпус. Теги и ограничения движков описаны в самих тестах и отчёте качества; skipped fault injections нельзя называть пройденными на другой платформе. Синтетический IME, WebKit и axe не доказывают работу системной клавиатуры, Safari на устройстве или экранного диктора.

Перед крупным выпуском пересмотреть матрицу браузеров/ОС по [08](../production/08-pwa-platforms.md) и провести платформенную приёмку. Перед каждым выпуском записать татарские [release notes](../../RELEASE_NOTES.tt.md) и внутренний [changelog](../../CHANGELOG.md). Любое изменение source scope аннулирует старую привязку одобрения: после последней правки пересобрать кандидата и пакет рецензента по [release-engineering.md](release-engineering.md). Не переносить approved на новый digest без настоящего заключения ответственного.

## Инцидент и восстановление

1. Зафиксировать симптом, IDs обоих выпусков, run ID, браузер/ОС и время. При подозрении на потерю данных, неправильный ключ или обход помощи прекратить новые публикации до разбора. Доступный согласованный экспорт сохранить до любых попыток восстановления; не очищать данные или кэши пользователя автоматически.
2. Проверить Check/candidate/deploy/Verify published site в Actions. Success одного deploy не означает last-good. Скачать оба bundle: известный хороший `last-good` и `release-candidate` текущего живого сайта. Проверить SHA, manifests и provenance через readReleaseBundle; взять полные свидетельства, а не отдельный произвольный tar.
3. Сопоставить live release-manifest.json с current. При ошибке/CDN-расхождении сначала установить, какие байты реально опубликованы. Истёкший/удалённый архив восстановить из внешней копии владельца; существующий процесс намеренно блокирует публикацию при потере истории. Не объявлять такой сайт первым выпуском. Возврат внешнего архива в автоматизацию требует отдельно проверенного восстановления его происхождения; подстановка run ID или самодельного last-good не допускается.
4. Выбрать совместимое исправление вперёд либо возврат сайта. Обычный forward fix возможен, когда живой выпуск совпадает с сохранённым last-good; он получает новый app/release ID, сохраняет поддерживаемую БД и проходит обычные gates. Если B уже опубликован, но его Verify published site failed и last-good остался A, прямой C будет заблокирован несовпадением live/last-good. Сначала выполнить успешный совместимый Restore A с сохранённым пакетом B, затем подготовить C. Если A отсутствует или Restore не проходит проверку текущей БД, требуется отдельный проверенный план восстановления происхождения/истории и данных; обычный pipeline не обещает исправить этот разрыв. Уже принявшие дефектный выпуск установки с target в previous сохраняют принятый reader: возврат Pages их не понижает и не отзывает офлайн-код. Им требуется совместимое исправление вперёд. При повреждённой/несовместимой БД нужен отдельный план восстановления, а не старый worker поверх новой схемы.
5. Для возврата сайта сначала локально извлечь известные bundle, проверить текущую БД и собрать retained package по [инструкции выпуска](release-engineering.md). После решения владельца открыть Actions → Restore known release → Run workflow → main, указать target_run_id и current_run_id. Это действие публикует сайт. Автоматизация проверит происхождение/срок/живой current, совместимость, новую тестовую БД, общий deploy и внешний smoke. Нельзя обходить её gate ради быстрого зелёного статуса.
6. После успешного Verify published site скачать новый last-good и записать, какие группы установок восстановлены, какой forward fix ещё нужен. Если smoke не прошёл, не считать инцидент закрытым и не назначать выпуск известным хорошим. После исправления добавить целевую регрессию, независимое ревью, заключение об исправлении и заметку ученику без технической перегрузки.

Архивы Actions истекают: last-good/release-candidate90 дней, полные quality traces14, обезличенная тестовая БД7. После каждого успешного выпуска владелец скачивает last-good и сохраняет вне Actions как минимум текущий и предыдущий известный выпуск с evidence/checksums/dependencies. Перед истечением проверить восстановление в новый каталог и сохранить SHA отдельно. Это ручная обязанность владельца; фоновый сервис или запланированная задача не создавались.

Новые аудио, аккаунты, OCR, рукописный ввод, русский курс и синхронизация требуют отдельного решения и этапа. Сопровождение v1 не вводит их скрыто.
