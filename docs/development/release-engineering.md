# Подготовка выпуска

Публичный адрес: https://halsab.github.io/isketatar/. Выпуск производится из main; локальная разработка и сборка сами ничего не публикуют. Внешние условия перечислены в external-acceptance.json. По решению владельца от 13.09.2026 pending сохраняется как фактический статус и не блокирует Actions.

## Кандидат и заключения

Использовать Node из .nvmrc и npm из packageManager. `npm ci`, `npm run check`, `npm run build` создают dist и quality-results/build-provenance.json. Build фиксирует базовый commit, признак незакоммиченных изменений, Node, release_id, manifest SHA-256, digest входов сборки и product scope. Локальная dirty-сборка допустима для разработки; опубликованный кандидат должен собираться из чистого checkout выбранного SHA.

product_artifact_sha256 включает реальные шаблонные байты HTML/JS/CSS/fonts/JSON, transport worker, версии/политики и shell graph. Из него исключён только built_at, который меняется после добавления отчёта отдельным коммитом. Полный release_id и build_inputs_sha256 включают timestamp и остаются уникальными для конкретного выпуска. Одобрение связывает и source scope, и исполняемый продукт; timestamp не подменяет кодовую идентичность.

После финальной сборки `node tools/build-review-package.mjs` создаёт пакет рецензента и отказывается работать при устаревшем scope/manifest. В итоговый отчёт включить product_scope_sha256, product_artifact_sha256, проверенный release_id и исполнителя. Сохранить настоящий отчёт в docs/development/acceptance-reports/; SHA-256 этого файла записать в report_sha256. Обновить соответствующую роль в external-acceptance.json. Формы, критерии и ответственность описаны в review-handoff.md; автоматическая проверка подтверждает связь файлов, но не содержание человеческого заключения.

`node tools/check-acceptance.mjs` проверяет структуру, права, привязку всех имеющихся одобрений и выводит ожидающие роли. `node tools/check-acceptance.mjs --require-approved` позволяет отдельно проверить полноту внешней приёмки и завершается ошибкой при любом pending; Actions этот необязательный режим не вызывает. Неверная дата, старый scope/продукт, изменённый отчёт, посторонний путь или symlink дают ошибку. Нельзя заменить pending на approved ради зелёного CI.

## Состав артефакта

Общая проверка tools/release-artifact.mjs использует тот же строгий manifest parser, что runtime. Разрешены текущий и максимум один предыдущий immutable package, стабильный sw.js и точные корневые копии текущего release. Проверяются размеры, SHA каждого ресурса, отсутствие лишних файлов/ссылок и общий предел. Контрольная сумма всего inventory охватывает также worker и root aliases, не входящие в assets manifest. Учебник, отчёты рецензентов, исходники, node_modules, карты исходников и секреты в публикацию не входят.

## Локальная доставка и упаковка

`npm run test:delivery` выполняет Chromium smoke двух immutable-пакетов: paused draft → принятие обновления → точное сравнение учебных stores/settings/positions и data_generation → запись нового draft новым кодом → откат сайта → проверка сохранения принятого reader и той же базы → новый офлайн-запуск. Отдельные чистые профили проверяют возвращённый предыдущий сайт и кандидата с их офлайн-уроками. Повторная публикация previous не понижает accepted release установленного приложения: прежний JS не открывается поверх текущей БД. Для уже принявших дефектный выпуск нужен новый совместимый выпуск с исправлением (forward fix), теми же gates и сохранением экспорта. Не обещать отзыв установленного кода одним откатом Pages. Никакие пользовательские профили не используются.

Если задан PREVIOUS_DIST, используется реальная предыдущая сборка. Без него создаётся явно помеченный bootstrap-same-code: тот же исполняемый продукт с другой датой и release_id. Проверяется равенство product_artifact_sha256. Это проверка механизма для первого выпуска, а не выдуманный исторический last-good. Различие progress/content schema или policy_versions требует отдельного плана совместимости и блокирует обычный rollback smoke. Успешное совпадение метаданных не заменяет браузерный сценарий.

`npm run prepare:release` проверяет актуальность provenance/scope, собирает quality-results/pages/ с текущим и предыдущим опубликованным пакетами (PREVIOUS_DIST), сохраняет полный inventory, dependency/license inventory и детерминированный artifact.tar в quality-results/release/. В CI дополнительно нужны clean checkout и совпадение GITHUB_SHA. Артефакт содержит только сайт; свидетельства лежат рядом. Не удалять предыдущий опубликованный пакет ради места.

`python3 tools/package-artifact.py extract ARCHIVE NEW_DIRECTORY SHA256` проверяет digest, размеры, пути, типы и дубликаты до записи файлов. Каталог назначения должен отсутствовать. Архив не содержит symlinks/hardlinks, source map или произвольный build output. После извлечения readReleaseBundle повторно проверяет manifest, полный inventory, dependencies и исходную provenance кандидата из release-evidence.json. Хранилище Actions с retention90 дней не является вечной резервной копией: владелец сохраняет каталог release вне истекающего хранилища до его удаления.

Для отката нельзя просто загрузить старый tar, удалив файлы уже принятой версии. `ROLLBACK_BUNDLE=... CURRENT_BUNDLE=... node tools/stage-rollback.mjs` извлекает два проверенных bundle в новые временные каталоги, собирает quality-results/rollback-pages/ и quality-results/rollback-release/. Корневые файлы/worker берутся из известной хорошей версии; последний принятый package сохраняется вторым immutable-каталогом. Такой же каталог обслуживается локальным smoke. Команда ничего не публикует. Перед реальным откатом нужны сохранённые доказательства выбранного известного выпуска, актуальное соответствие current опубликованному сайту и проверка поведения установленной версии; несовместимые схемы/политики блокируются.

## CI и автоматическая публикация

check.yml запускается на PR, push в main и вручную. Check получает только contents:read, устанавливает закреплённые Node/npm/dependencies, проверяет content/schema/types/unit/tools и собирает один artifact. PR и main выполняют `npm run test:smoke`:15 существующих Chromium-сценариев с тегом @smoke. Они проверяют запуск/прямой URL, идентичность release, атомарность IndexedDB, сохранение черновика, проверку ответа, импорт/экспорт, отказ хранения, несовместимые схемы, холодный офлайн всех модулей, восстановление ресурса и обновление двух окон. Содержательные assertions не ослаблены.

Полный набор Chromium/Firefox/WebKit, включая @full, и20 лабораторных замеров запускаются через Actions → Check and release → Run workflow. Ручной аудит не создаёт candidate и ничего не публикует. Его результаты доступны в artifact quality14 дней; отсутствие performance.json в обычном release bundle допустимо. При изменениях контента, формата хранения или закрепления старых уроков дополнительно запускать адресные retained/update тесты либо полный аудит по maintenance.md.

Check выполняется в официальном Ubuntu Noble образе Playwright1.63.0, закреплённом digest; браузеры и системные библиотеки уже входят в образ. Сразу после checkout отдельный shell-шаг добавляет только `$GITHUB_WORKSPACE` в global safe.directory текущего job: checkout настраивает Git через временный HOME, который не используется последующими shell-шагами. Исключение соответствует [механизму Git safe.directory](https://git-scm.com/docs/git-config#Documentation/git-config.txt-safedirectory); wildcard не применяется. При обновлении Playwright согласованно обновлять package-lock и digest образа.

Один worker сохраняет ресурсы для PWA-окон и service worker. В CI разрешён один повтор упавшего теста и10s на обычное ожидание интерфейса; повторная ошибка блокирует job, а восстановившийся тест отмечается flaky в JSON и trace. Локально остаются retries0 и5s. Это штатные [повторы Playwright](https://playwright.dev/docs/test-retries), не игнорирование exit code. Лимит check15 минут для PR/main,45 минут для ручного полного аудита. Сборка, размерные бюджеты, права, целостность архива и проверки доставки остаются обязательными.

Candidate получает contents:read/actions:read, восстанавливает уже проверенный artifact по ID/digest, не компилирует его повторно и повторно проверяет права и достоверность имеющихся отчётов. Он выбирает last-good только из успешных публикаций main в известных workflow, сравнивает его с живым manifest и сохраняет предыдущий пакет. Истёкший/потерянный archive или несовпадение живого сайта блокирует выпуск;404 считается первым выпуском только при отсутствии истории и страницы. После delivery smoke создаётся свежая обезличенная тестовая БД на предыдущем опубликованном сайте. Это исключительно данные сценария «әңгәмә», не профиль пользователя. Сохраняется storageState с IndexedDB, без cookies и Cache Storage; лимит1MB, retention7 дней.

Publish вызывается только этими production workflow. Отдельный deploy job проверяет protected main, актуальный head, принадлежность artifact текущему run и SHA самого tar. Только он исполняет Pages deploy с pages:write/id-token:write через github-pages; checkout, npm install и build в нём отсутствуют. Используется уже проверенный tar, actions закреплены полными commit SHA. Публикации и откаты разделяют concurrency pages-production без отмены активного run. Новая main-версия перед deploy делает старый кандидат неактуальным.

После deploy отдельный job с contents:read сверяет SHA/размер/MIME **всех** опубликованных файлов (включая worker и retained package), проверяет чистый браузер, прямой урок и холодный офлайн. При наличии предыдущей БД он восстанавливает её без кэшей, явно открывает принятую версию, получает право записи в новом тестовом окне, проверяет неизменность stores/settings/positions/generation, принимает кандидата и восстанавливает черновик. Ранняя версия не открывается поверх другой принятой БД. Для распространения CDN допускаются три проверки с паузой5s; несовпадение остаётся ошибкой, а не успешным выпуском.

Только после успешного внешнего smoke создаётся last-good на90 дней: tar, inventory, зависимости/лицензии, provenance, сохранённый acceptance и delivery/published smoke. Performance из старых bundle сохраняется при откате, если присутствует; новые релизы его не требуют. E2E traces и результаты ручного performance-аудита живут14 дней. Сохраните release bundle вне Actions до истечения90 дней. Наличие deploy success без published smoke и last-good не означает успешный выпуск. Проверка следующей версии обнаружит такой разрыв и потребует разобрать инцидент.

Процесс соответствует [Pages custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [параметрам deploy-pages](https://github.com/actions/deploy-pages), [проверке digest при download-artifact](https://github.com/actions/download-artifact) и [хранению artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data). Pages tar загружается напрямую pinned upload-artifact: нет вложенного composite action с плавающей версией.

## Управляемый откат

rollback.yml запускается только вручную из protected main и требует два числовых run ID: успешный target с last-good и current с release-candidate, совпадающий с живым сайтом. Current может относиться к выпуску, у которого post-deploy smoke завершился ошибкой. PR/fork/произвольные workflow и истёкшие archives не принимаются. Целевой artifact сохраняет исходные SHA, фактические статусы внешних проверок и performance evidence; pending допустим, имеющиеся approved должны соответствовать исходному продукту; действующее подтверждение прав тоже проверяется. Сборка кода не повторяется.

Перед публикацией выполняются compatibility/delivery и свежий профиль текущего сайта; rollback сохраняет current package и использует общий publish/smoke. Неуспех проверки текущей БД блокирует автоматический откат и требует совместимого исправления вперёд. После отката старый сайт доступен новым установкам; уже принятая установка, имеющая этот target в previous, сохраняет свой reader. Откат не удаляет IndexedDB, не отменяет сделанные миграции и не отзывает офлайн-код. Для таких установок нужен новый совместимый release_id с исправлением.

Техническое исправление Actions проверяется без push и публикации из локальной разработки. Фактические настройки репозитория и результаты локальной проверки фиксируются в implementation.md/release-conditions.md; pending внешней приёмки сохраняется.
