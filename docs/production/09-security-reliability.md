# Сохранность, безопасность и приватность

Контракт будущей реализации. Формат записей, пределы и транзакционные инварианты определены в [02](02-data-contracts.md); этот документ задаёт порядок работы при конкуренции, отказах и недоверенном вводе. Сетевая поставка и кэши принадлежат [08](08-pwa-platforms.md). Здесь нет заявления, что приложение уже прошло проверку безопасности.

## 1. Границы доверия

Приложение служит самостоятельному обучению. Ответы и ключи статического курса доступны владельцу браузера; локальный результат не является защищённым экзаменом, удостоверением личности или сертификатом. Не усложнять приложение шифрованием ключей, которое браузер обязан самостоятельно расшифровать.

Доверенные входы сборки — проверенный редакционный корпус, закреплённые зависимости и лицензированные шрифты. Недоверенные входы runtime — URL, пользовательский ввод, импорт, имя файла, сообщения вкладок/worker и повреждённое хранилище. Статус «локальный» не отменяет валидацию. Хеш пакета выявляет повреждение и смешение версий; компрометацию той же сборки он не устраняет.

На Pages соседние проекты `owner.github.io/a/` и `/isketatar/` имеют один origin. Префиксы кэшей и имя БД предотвращают случайные коллизии, но не изолируют данные от исполняемого кода соседнего проекта. Недоверенные preview размещаются на другом origin; при необходимости отдельной изоляции production получает собственный домен с предусмотренным переносом прогресса. Это следует из [модели нескольких PWA на одном origin](https://web.dev/articles/building-multiple-pwas-on-the-same-domain).

## 2. Запись результата и черновика

Команда submit получает неизменяемый снимок введённого ответа, presentation_id, ожидаемые data_generation/writer_epoch и предметные revisions. Проверка ответа — чистая функция на закреплённой версии ключа. Репозиторий повторно проверяет ожидания в общей readwrite-транзакции, сохраняет Attempt, Presentation, Session, exposure и SRS; UI показывает сохранённый результат только после completion всей транзакции. Повтор с тем же ID и payload возвращает прежний результат, иной payload получает конфликт.

Черновик текстового ответа сохраняется после 300 ms без ввода; выбор варианта/набора и переход «Следующий» запускают сохранение сразу. При composition не фиксировать промежуточную строку как законченный ответ: сохранение выполняется после compositionend. Перед намеренной навигацией, паузой, экспортом и обновлением очередь записи завершается. Индикатор различает «сохраняется», «сохранено» и «не сохранено»; отсутствие ошибки fetch не означает сохранность ответа.

События visibilitychange/pagehide дают дополнительную попытку записать уже подготовленный снимок, но unload не является гарантией. После аварийного завершения восстанавливается последний подтверждённый draft, а не обещается последний введённый символ. Долгие вычисления, сеть, диалоги и ожидание другого tab не выполняются внутри IDB-транзакции: подготовка идёт до неё, CAS и запись — в ней. Особенности жизненного цикла транзакций описаны в [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB).

Пользовательские данные и CacheStorage имеют независимые статусы. Удаление скачанного курса не очищает БД. Обновление worker не изменяет ответы. Сбой записи не маскируется оптимистическим баллом; доступен повтор той же команды либо явный переход к работе в памяти.

## 3. Несколько вкладок

Есть один владелец изменяемого учебного состояния. Первое получение свободного writer_id и любая передача происходят атомарно через control. Другие вкладки читают курс и прогресс, но не отправляют ответы, не меняют черновик, настройки, закладки и расписание без явного «Продолжить здесь». Передача повышает writer_epoch; старая вкладка теряет право записи независимо от того, получила ли уведомление. Истечение таймера само по себе не создаёт нового владельца. После закрытой или зависшей вкладки пользователь может явно взять управление без ожидания успешного unload.

BroadcastChannel передаёт только тип события, data_generation и state_revision после commit. Получатель перечитывает БД; тело сообщения не становится состоянием и не даёт полномочий. При отсутствии BroadcastChannel достаточно повторной проверки на focus/visibilitychange и перед любой записью; для видимой страницы допустимо сверять revision раз в 2 секунды. Корректность обеспечивают транзакции, а не своевременность таймера. Обновления UI подписываются на согласованный снимок репозитория.

**Исключение — монотонные наблюдения показа и помощи.** Любая вкладка вправе отдельной короткой транзакцией записать фактический exposure и помощь, не получая writer_epoch. Это необходимо, чтобы чтение словаря во второй вкладке учитывалось в отложенной проверке первой. Такая команда проверяет ожидаемую data_generation, разрешённый материал и текущие записи внутри транзакции; не принимает готовые session/grade от вызывающего кода. Она может только установить ещё пустой first-time, расширить множество раскрытой помощи, увеличить last_seen и пометить все текущие active/paused diagnostic/final как assisted. Черновики, ответы и расписание не меняются. Затронутые Session/Presentation.revision и общая state_revision увеличиваются.

Материал раскрывается **после commit наблюдения**, если он влияет на незавершённую проверку. Если submit первой вкладки успел раньше, помощь не меняет уже отправленный результат; если помощь записана раньше, устаревший submit получает конфликт. Первая вкладка перечитывает флаг и предлагает отправить сохранившийся ввод с учётом помощи. Она не повторяет автоматически старую команду под новыми токенами. Повторное открытие уже учтённой помощи идемпотентно.

При невозможности записать обязательный флаг содержимое остаётся закрытым с действием повтора/восстановления. Нельзя открыть ответ и оставить durable-проверку «самостоятельной» после reload. Обычное чтение без затронутой незавершённой проверки доступно даже при сбое exposure, но UI не утверждает новизну материала. В действительно отдельном режиме только памяти помощь и оценки согласуются в одном снимке. Копирование durable-сеанса в память не отменяет обязательную запись помощи в известные непомеченные active/paused проверки исходной БД: до успешной записи их флага либо успешного durable reset помощь остаётся закрытой. Возврат к БД/reload не должен восстанавливать тот же сеанс как самостоятельный после раскрытия в ветви. Это не синхронизация с другими браузерами или установками.

Импорт/reset меняет data_generation. Любые поздние callback, старый preview, событие помощи и отложенный ответ прежнего набора отвергаются. Новые полномочия получает только новая явная команда после перечитывания состояния. Атомарная передача writer не равна новому Session и не переставляет варианты ответа. Технический update_gate из 02/08 проверяется каждой командой: в quiescing разрешены только завершение уже начатой записи, flush/pause, необходимое наблюдение до ACK и команды протокола; после ACK вкладка не начинает новые действия. В commit запрещены все пользовательские мутации, включая наблюдения помощи, import/reset и takeover, до подтверждённого завершения/отмены обновления. Сам gate не меняет оценки и не экспортируется.

## 4. Работа без постоянного хранения

Поддержка IndexedDB проверяется открытием и небольшой реальной транзакцией, а не user-agent. При ошибке открытия/QuotaExceeded/abort текущий сохранённый набор не удаляется. Различаются storage_unavailable, storage_full, storage_blocked и write_conflict; повтор не должен бесконечно мигать и создавать новые попытки.

Перед переходом в память останавливаются debounce/retry, завершается либо явно отменяется текущая очередь команд; новые callback привязываются к конкретному экземпляру репозитория и не перенаправляются автоматически при восстановлении БД. Если БД читается, берётся согласованный снимок. Он становится отдельной несохранённой ветвью с заметной постоянной подписью. Её можно экспортировать в стандартном формате. После восстановления БД ветвь не сливается автоматически: пользователь проверяет и импортирует файл обычной заменой или возвращается к прежнему сохранённому набору с явным объяснением потери несохранённых изменений. Если первоначальная БД не читается, память стартует с пустого набора; прежние данные не объявляются удалёнными.

navigator.storage.persist() — дополнительная возможность после осмысленного действия, а не гарантия. Объём estimate приблизителен. Браузер, ОС, приватный профиль или сам пользователь могут удалить хранилище; офлайн-установка не является резервной копией. Политики квот и вытеснения различаются: [MDN Storage](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [WebKit Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/).

Мягкий порог 16 MiB экспортируемых записей или 90 000 Attempts и жёсткие пределы 20 MiB/100 000 Attempts берутся из 02. Дельты размера учитываются в общей транзакции. При history_full накопление истории останавливается, экспорт и чтение остаются. Запись обязательного флага помощи также подчиняется ограничениям: отказ означает отсутствие раскрытия, а не молчаливую потерю флага. Никакого автоматического удаления старых ошибок ради свободного места.

## 5. Экспорт и недоверенный импорт

Экспорт читает все пользовательские stores в одном readonly-снимке после текущей записи. JSON UTF-8 сериализуется с проверкой итогового размера. Имя содержит продукт и числовую дату, не имя пользователя или ответ. Базовый перенос — Blob/download и выбор файла через input; системное share используется только при поддержке и явном действии. Object URL отзывается после завершения взаимодействия, не до начала скачивания. «Файл подготовлен» не означает, что браузер подтвердил сохранение на диск.

Импорт проходит этапы: проверка File.size → ограниченное чтение байтов и TextDecoder UTF-8 с fatal=true → JSON.parse → закрытая структурная схема → внутренние связи и лимиты → совместимость ключей/политик → согласованный preview → явная транзакционная замена. Cancel до commit ничего не меняет. При ошибке транзакции сохраняется весь прежний набор. Повторный импорт заменяет набор, не удваивает попытки.

Все числовые поля конечны и укладываются в безопасные пределы. Неизвестная схема и повреждённые ссылки отклоняются; структурно допустимые неизвестные старые ContentId/revision переходят в legacy согласно 02. Не подставлять новый ключ вместо старого. Вложенность разрешается только там и той глубины, которую допускает закрытая схема: произвольные рекурсивные объекты запрещены. После JSON.parse ограниченный итеративный обход со стеком отвергает глубину больше 32 до запуска валидаторов; максимальный допустимый экспорт проверяется на соответствие этому порогу. Не писать собственный JSON-парсер и не обходить недоверенную вложенность рекурсивной функцией. Сам вход уже ограничен 20 MiB.

JSON.parse не выполняет код; опасность появляется при дальнейшей обработке. Нельзя использовать eval, Function, raw HTML, произвольные URL или recursive merge импортированного объекта. Закрытые схемы отвергают `__proto__`, `constructor`, `prototype` в позициях ключей; переменные словари используют Map/объект без прототипа. В допустимом текстовом ответе эти последовательности остаются обычным текстом. Пользовательский текст выводится экранированным React-renderer, имя файла — также. [MDN prototype pollution](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/Prototype_pollution).

Ajv компилирует standalone-валидаторы **при сборке**. Runtime импортирует готовые функции, не вызывает compile с new Function и не требует unsafe-eval. Схемы и сгенерированный вывод проверяются в CI вместе. Это предусмотрено [Ajv standalone](https://ajv.js.org/standalone.html).

Замена preview защищена expected data_generation/state_revision. Любое изменение прогресса, включая помощь во второй вкладке, требует нового preview. Writer-право, идентичность вкладки и cache не импортируются. Active-сессии становятся paused; несовместимые черновики сохраняются как история. Перед заменой доступен экспорт текущего набора, но не навязывается фиктивная обязательная регистрация.

## 6. CSP и сетевые ресурсы

Production HTML содержит ранний CSP meta сразу после charset и до исполняемых ресурсов. Проектная исходная политика: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; worker-src 'self'; manifest-src 'self'; object-src 'none'; frame-src 'none'; base-uri 'none'; form-action 'none'. Конкретная итоговая строка проверяется на собранном dist. Для настоящей необходимой inline-темы допускается только build-generated hash точного скрипта; постоянный nonce и unsafe-inline JavaScript не используются. CSS Modules извлекаются в файл. Стили размеров выбираются классами из конечного списка, а не динамическими style-атрибутами; WAAPI/движение проверяются под действующей политикой.

Политика meta не даёт frame-ancestors, sandbox, Report-Only и полноценного reporting; произвольные response headers стандартный Pages-контур не настраивает. Нельзя заявлять защиту от framing только по meta. Worker-src ограничивает создание worker, но не заменяет политику его fetch. Worker обслуживает только разрешённые GET внутри base_path, проверенные URL/типы/статусы/хеши. Opaque, неожиданный redirect и HTML вместо JSON не попадают в пакет. Сообщения worker имеют закрытый enum команд и не принимают произвольный URL для cache. [MDN CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP), [ограничения meta CSP](https://developer.chrome.com/docs/lighthouse/best-practices/csp-xss), [CSP workers](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy#csp_in_workers).

Нет сторонних font CDN, analytics SDK, удалённых проверок ответа, API-ключей и пользовательского HTML. Clipboard/share/внешняя ссылка выполняются только после действия пользователя; копируемая публичная ссылка собирается из разрешённых полей по 05. Technical error details не включают answer_raw, историю, импорт или полный URL поиска.

## 7. Миграции, сброс и инциденты

Миграции добавочные и транзакционные; версии физической БД и обменной схемы различаются. versionchange закрывает соединение другой вкладки и показывает необходимость обновить его; blocked не запускает deleteDatabase. Чтение более новой неподдерживаемой схемы предлагает совместимое приложение/экспорт через поддерживаемый reader, не обещает разобрать неизвестные записи старым кодом. Откат хостинга не откатывает БД; матрица совместимости выпуска обязана это учитывать.

Reset прогресса требует отдельного подтверждения с объяснением, что будут удалены ответы, черновики, закладки, настройки и история повторений этого локального набора. Операция атомарно создаёт новый data_generation, очищает пользовательские stores и возвращает defaults; кэш курса остаётся. Другие вкладки перечитывают пустой набор, старые callback не восстанавливают удалённое. Удаление офлайн-пакета имеет другое действие и не меняет data_generation. Очистка только памяти не объявляется удалением сохранённого прогресса: полный reset успешен лишь после durable transaction. При недоступной БД остаётся ошибка; отдельно можно отказаться от несохранённой ветви.

При дефекте оценивания сохраняют исходные Attempts и revision, исправляют ключ/политику новым release, явно обозначают необходимость новой проверки. При дефекте миграции выпуск останавливают, сохраняют last-good artifact, предлагают безопасный экспорт и совместимое исправление. При подозрении на вредоносную сборку исправляют цепочку выпуска и worker по прежнему URL; удаление сайта из сети не отзывает уже сохранённую офлайн-копию. Не обещать немедленный контакт с устройством без сети.

## 8. Данные, которые продукт действительно собирает

В первой версии приложение не отправляет ответы, имя, закладки или расписание разработчику, не использует аккаунт и собственную аналитику. GitHub получает технические запросы к размещённому сайту и может сохранять IP для безопасности; это следует отдельно указать в татарском privacy-тексте. [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).

Метрики пилота получают только при согласованном исследовании с участниками; никаких скрытых сетевых событий ради будущих графиков. Если аналитика, синхронизация, серверный словарь или аккаунт появятся позднее, это отдельное решение о продукте, данных и согласии. Настоящий контракт не разрешает добавить их автоматически.

## 9. Приёмка надёжности

Обязательные сценарии: двойной submit; abort после записи одного request; ввод и аварийное закрытие; takeover без unload; помощь из второй вкладки раньше/позже submit; late callback после import/reset; потеря BroadcastChannel; quota при помощи и ответе; восстановление из памяти через файл; 20 MiB boundary; глубокий JSON; опасные ключи; неизвестная revision; устаревший preview; миграция blocked; CSP без unsafe-eval; удаление кэша при сохранённой истории. Ожидаемые исходы определены выше и в 02; конкретный исполняемый набор входит в [план качества](10-quality-release.md). Проверка документа не считается выполнением этих будущих тестов.
